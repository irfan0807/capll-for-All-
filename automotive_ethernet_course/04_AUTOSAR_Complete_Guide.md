## 4.1 AUTOSAR OVERVIEW

### What Is AUTOSAR?

**AUTOSAR** (AUTomotive Open System ARchitecture) is an open industry standard for automotive software architecture. It was founded by BMW, Bosch, Continental, Daimler, and Volkswagen in 2003. It defines how software modules are structured, configured, and integrated across ECUs from different vendors.

### Two AUTOSAR Generations

```
┌──────────────────────────────────────────────────────────────────────┐
│                    AUTOSAR CLASSIC (CP)                              │
│  Version: 4.x series (current: 4.4.0)                               │
│  MCU: Microcontrollers (Aurix, S32K, RH850)                         │
│  OS: AUTOSAR OS (OSEK-based, tasks with fixed memory)               │
│  Communication: Signal-based (PDU/Signal via COM stack)             │
│  Language: C (no C++ dynamic features)                              │
│  Safety: ASIL-D support with lockstep                               │
│  Use Case: Powertrain, Body, Chassis, Safety ECU                    │
├──────────────────────────────────────────────────────────────────────┤
│                    AUTOSAR ADAPTIVE (AP)                             │
│  Version: R22-11 (current)                                          │
│  MCU: High-performance SoCs (S32G, R-Car, TDA4)                    │
│  OS: POSIX (QNX, Linux) — dynamic scheduling                        │
│  Communication: Service-oriented via SOME/IP                        │
│  Language: C++14/17 (STL, dynamic memory allowed)                  │
│  Safety: Mixed-criticality possible                                 │
```

## 4.3 MCAL — MICROCONTROLLER ABSTRACTION LAYER

### What MCAL Does

MCAL provides hardware-independent APIs for the ECU Abstraction Layer. Chip vendors (NXP, Infineon, Renesas) supply MCAL drivers certified for their silicon.

### Key MCAL Modules

| MCAL Module | Function | Key API |
|------------|---------|---------|
| **Eth** | Ethernet MAC driver | `Eth_Transmit()`, `Eth_Receive()` |
| **EthTrcv** | Ethernet PHY driver | `EthTrcv_SetTransceiverMode()` |
| **Can** | CAN controller driver | `Can_Write()`, `Can_SetControllerMode()` |
| **Spi** | SPI bus driver | `Spi_SyncTransmit()` |
| **Adc** | Analog-to-Digital converter | `Adc_StartGroupConversion()` |
| **Gpt** | General Purpose Timer | `Gpt_StartTimer()` |
| **Wdg** | Watchdog driver | `Wdg_SetTriggerCondition()` |
| **Fls** | Flash driver | `Fls_Write()`, `Fls_Erase()` |
| **Dio** | Digital I/O | `Dio_WriteChannel()`, `Dio_ReadPort()` |
| **Pwm** | PWM generator | `Pwm_SetDutyCycle()` |

### MCAL Eth Driver — Ethernet Frame Transmit

```c
/* AUTOSAR MCAL Eth — Transmit Ethernet Frame */

/* Step 1: Provide a TX buffer from the Ethernet controller */
Std_ReturnType result;
uint8* pDataPtr;
uint16 lenByte = 0U;

result = Eth_ProvideTxBuffer(CTRL_IDX_ETH0, &buffIdx, &pDataPtr, &lenByte);

if (result == BUFREQ_OK) {
    /* Step 2: Fill in the Ethernet frame payload */
    (void)memcpy(pDataPtr, someipPayload, payloadLength);
    
    /* Step 3: Transmit the frame */
    result = Eth_Transmit(
        CTRL_IDX_ETH0,    /* Controller index */
        buffIdx,           /* Buffer index from ProvideTxBuffer */
        ETH_FRAMETYPE_IPV4, /* EtherType = 0x0800 */
        TRUE,              /* Send with CRC */
        payloadLength,
        destMacAddr        /* Destination MAC */
    );
}

/* Transmission complete notification — called by ISR */
void EthIf_TxConfirmation(uint8 CtrlIdx, Eth_BufIdxType BufIdx) {
    /* Buffer released, transmission confirmed */
    Com_TxConfirmation(BufIdx);
}
```

## 4.6 PDU ROUTER (PduR)

### PduR — The Traffic Director

PduR is the central routing hub. Every PDU going up or down the communication stack passes through PduR. It enables gateway functionality (route CAN PDU to Ethernet and vice versa).

```
PDU ROUTING TABLE EXAMPLE (CAN → Ethernet Gateway):
┌──────────────────────────────────────────────────────────────────┐
│  SOURCE MODULE │ SOURCE PDU ID │ DEST MODULE │ DEST PDU ID       │
├──────────────────────────────────────────────────────────────────┤
│  CanIf_Rx      │ 0x001 (CAN)   │ EthIf_Tx    │ 0x100 (Ethernet) │
│  EthIf_Rx      │ 0x100 (Eth)   │ CanIf_Tx    │ 0x001 (CAN)      │
│  COM           │ 0x200         │ PduR_Tx     │ CanIf (local)    │
│  DCM           │ 0x300 (UDS)   │ CanTp / DoIP│ 0x7DF            │
└──────────────────────────────────────────────────────────────────┘

Gateway ECU routing CAN vehicle speed to Ethernet:
CAN:0x201 received ──► CanIf ──► PduR ──► EthIf ──► Eth:0x100 transmitted
```

## 4.9 DEM — DIAGNOSTIC EVENT MANAGER

### DEM Role — Fault Reporting & DTC Storage

DEM manages Diagnostic Trouble Codes (DTCs). When a software component detects a fault (e.g., RADAR sensor timeout), it reports to DEM. DEM stores the fault data in NvM and makes it accessible to DCM for reading via UDS 0x19.

```c
/* SWC reporting a fault to DEM */

/* FCW algorithm detects RADAR signal lost */
if (radarTimeout > RADAR_TIMEOUT_MS) {
    /* Report fault to DEM */
    (void)Dem_ReportErrorStatus(
        DEM_EVENT_ID_RADAR_TIMEOUT,      /* Configured DTC event ID */
        DEM_EVENT_STATUS_FAILED          /* FAILED / PASSED / PREPASSED */
    );
}

/* DEM internally:
   1. Counts consecutive failures vs debounce threshold
   2. When threshold reached: DTC = CONFIRMED, stored in NvM
   3. Snapshot data (freeze frame) stored: timestamp, speed, voltage
   4. DTC accessible via UDS 0x19 ReadDTC service
*/

/* Clearing faults after repair */
Dem_ClearDTC(DEM_DTC_GROUP_ALL);  /* Clears all DTCs */
```

### DEM Fault State Machine

```
DEM DTC STATE MACHINE:
                   ┌─────────────────────┐
         FAILED    │                     │ PASSED
         report    │    TEST_FAILED      │ report
   ─────────────►  │    (Pending DTC)    │ ──────────────►
   if >= debounce  │                     │  if >= debounce
   threshold       └─────────┬───────────┘  threshold
                             │ Enough consecutive fails
                             ▼
                   ┌─────────────────────┐
                   │    CONFIRMED DTC    │ ← stored in NvM
                   │    (Fault Memory)   │ ← visible via 0x19
                   └─────────────────────┘
```

## 4.12 AUTOSAR OS LAYER

### Task, Event, Alarm Relationships

```c
/* AUTOSAR OS Configuration (OIL format / ARXML) */

TASK ADAS_Task_10ms {
    PRIORITY = 50;
    SCHEDULE = FULL;     /* Preemptable */
    ACTIVATION = 1;
    AUTOSTART = FALSE;
    RESOURCE = ADAS_Mutex;
};

ALARM ADAS_Alarm_10ms {
    COUNTER = OsSystemCounter;
    ACTION = ACTIVATETASK { TASK = ADAS_Task_10ms; };
    AUTOSTART = TRUE { ALARMTIME = 10; CYCLETIME = 10; }; /* 10ms cycle */
};

EVENT ADAS_DataReady {
    MASK = 0x0001;
};

/* Task implementation */
TASK(ADAS_Task_10ms)
{
    EventMaskType events;

    /* Wait for data-ready event from Ethernet Rx ISR */
    WaitEvent(ADAS_DataReady);
    GetEvent(ADAS_Task_10ms, &events);
    ClearEvent(ADAS_DataReady);

    if (events & ADAS_DataReady) {
        ADAS_ProcessRadarData();
        ADAS_RunFCWAlgorithm();
        ADAS_TransmitWarning();
    }

    TerminateTask();
}
```

## 4.14 ETHERNET STACK INTEGRATION — DEBUGGING CASES

### Debug Case 1: SOME/IP Event Not Received by Client

```
SYMPTOM: ADAS ECU not receiving RADAR Object SOME/IP events

DEBUG STEPS:
1. Check SD logs in CANoe — is OfferService seen?
   ├── If NO: RADAR ECU SD not configured or SD task not running
   └── If YES: Continue

2. Check SubscribeEventgroup in CANoe — is client subscribing?
   ├── If NO: Client SD configuration wrong (EventGroupId mismatch)
   └── If YES: Continue

3. Check SoAd socket state — is UDP socket open?
   ├── CANoe: EthIf diagnostic → SoAd socket status
   └── Symptom: ONLINE_ACTIVE vs OFFLINE

4. Check IP configuration — can ECUs ping each other?
   ├── ARP table check: does ADAS ECU know RADAR ECU MAC?
   └── IP subnet mismatch → SoAd cannot route

5. Check SOME/IP payload size against buffer configuration:
   └── SoAd Rx buffer too small → frames silently dropped

ROOT CAUSE FOUND: EventGroupId in SD subscriber config was 0x0001
but server offered EventGroupId 0x0002 → subscription never matched
FIX: Update ARXML SD configuration to match EventGroupIds
```

### Debug Case 2: Ethernet Link Down After 30 Seconds

```
SYMPTOM: 100BASE-T1 link drops after ~30s of operation

DEBUG STEPS:
1. EthTrcv diagnostic register via MDIO:
   PHY_STATUS_REG: Link=UP → Link=DOWN at 30s

2. Check EthSM (Ethernet State Manager) log:
   EthSM_NetworkMode transitions: ONLINE → OFFLINE

3. Measure cable: Length, connector crimp quality
   → Within spec (8m of STP)

4. Check for EMI — route near ignition coil?
   → Routing was 5cm from high-voltage wiring

5. MDIO EEE (Energy Efficient Ethernet) register:
   PHY_EEE_CTRL: EEE_ENABLE = 1 (should be disabled for automotive)
   → EEE was causing false sleep mode under vehicle EMI

ROOT CAUSE: EEE enabled on TJA1100 PHY
FIX: EthTrcv_SetTransceiverMode disables EEE via MDIO write
     to TJA1100 register 0x11, bit 2 (EEE_CAPABLE = 0)
```

## 4.15 INTERVIEW QUESTIONS — SECTION 4

**Q1: Explain the AUTOSAR layered architecture. What is the role of RTE?**

> AUTOSAR Classic uses a 3-layer architecture: ASW (Application), RTE (Runtime Environment), and BSW (Base Software) + MCAL + Hardware. The RTE is a generated layer that decouples SWCs from BSW. It maps S/R port writes to COM module APIs and C/S port calls to service functions. SWCs communicate only via RTE — they never call BSW directly. This enables SW reuse across different hardware platforms.

**Q2: What is PduR and what function does it perform?**

> PduR (PDU Router) is the communication gateway module that routes PDUs between any communication module pair. It enables: (1) fanout — one COM PDU broadcast to both CAN and Ethernet; (2) gateway — CAN Rx PDU directly forwarded to Eth Tx; (3) multiplexing. Every AUTOSAR communication goes through PduR. It uses a static routing table configured in ARXML/DaVinci that maps source module + PDU ID to destination module + PDU ID.

**Q3: How does DEM and NvM interact for DTC storage?**

> When DEM confirms a fault (after debounce), it calls NvM to write the DTC and snapshot data (freeze frame) to non-volatile memory. DEM uses dedicated NvM blocks configured per DTC — storing status bits, occurrence counter, and environmental data. On ECU restart, NvM_ReadAll() restores DEM's fault memory. DTCs survive power cycles until explicitly cleared by the tester via UDS 0x14 service.

**Q4: What is the complete Ethernet TX call chain in AUTOSAR Classic?**

> SWC calls `RTE_Write()` → COM serializes signal → `PduR_ComTransmit()` → `SoAd_IfTransmit()` (SOME/IP path) → `TcpIp_UdpTransmit()` → `EthIf_Transmit()` → `Eth_Transmit()` (MCAL) → `EthTrcv` (PHY configured) → 100BASE-T1 wire.

**Q5: What is the difference between AUTOSAR Classic and Adaptive?**

> Classic uses C on microcontrollers with OSEK-based RTOS, static memory allocation (no heap), and signal-based communication via COM. Adaptive uses C++ on Linux/QNX SoCs with POSIX APIs, dynamic memory and services allowed, and service-oriented communication via SOME/IP through the ARA framework. Adaptive is designed for high-compute ADAS/IVI where processing power and OTA flexibility matter more than hard real-time.
